Methodology

Each benchmark class compares strategies for one P/Invoke shape — buffer-out, string-in, struct passing, callback, etc. All variants in a class call the same native function, so timing differences come from the .NET marshalling/transition layer rather than native work. The native shim is a tiny Zig library compiled with -Doptimize=ReleaseFast.

Times below are Mean from --job Short (3 warmup + 3 iterations × 1 launch). The x-axis is log-scale, so a bar twice as long is roughly 10× slower. Parameterized classes (Size, Length × Pay, ArrayLen) are faceted by parameter.

NoopBenchmarks

Pure transition cost — the native side returns immediately, so what's measured is the cost of crossing the managed/unmanaged boundary plus any IL stub work. This is the floor for every other P/Invoke measurement; subtract these numbers from comparable variants elsewhere to isolate "what the marshalling actually adds."

LibraryImport_Span_SuppressGC is the headline figure — at well under 2 ns it's roughly an order of magnitude cheaper than the cooperative-transition variants. Only safe when the native side is short, non-blocking, and doesn't call back into managed code.

FillBenchmarks

Five strategies for passing a writable byte buffer to a native memset-shaped function. byte[] with the runtime stub pinning the array (V1) is the long-standing "obvious" shape; byte* + fixed (V2) and ref byte (V3) are the unsafe / by-ref equivalents the modern .NET ecosystem prefers.

On net8+, the three DllImport variants and the LibraryImport variants typically converge within 1–2 ns at small sizes because the JIT folds them to the same call site. At Size = 4096 the actual memset work dominates and the strategy choice becomes invisible. The SuppressGC variants stay flat at ~2 ns until the memset cost overtakes the transition saving.

StringBenchmarks

UTF-8 string marshalling, the most-asked-about category for non-Windows-codepage interop. Variants cover the historical surface: legacy ANSI (default, CharSet.Ansi, [LPStr] — all aliases on Windows), per-parameter UTF-8 ([LPUTF8Str]), the source-generated StringMarshalling.Utf8, hand-rolled stackalloc/pool encoding, and pre-encoded byte buffers.

The interesting comparisons:

  • Pre-encoded vs runtime-encoded: DllImport_PreEncoded / LibraryImport_ROSpan beat LibraryImport_Utf8 by a large margin at every payload size, because the runtime encoders allocate a fresh buffer per call.
  • Payload class: ASCII (1 byte/char), Latin-1 (2 bytes/char with umlaut), CJK (3 bytes/char). Per-call encoding cost scales with the byte count, not the .NET string length.
  • CharSet.Auto on Windows quietly marshals UTF-16, which the UTF-8 strlen here misinterprets — the timing is meaningful but the return value is nonsense. Useful demonstration of a real footgun.

StringNoopBenchmarks

Same variants as StringBenchmarks but pointed at a native function that returns 0 immediately. Subtract row-by-row from StringBenchmarks to isolate the "native walk" contribution from the .NET-side encoding+transition cost. For small Length values, the noop and non-noop numbers are nearly identical — the work is dominated by marshalling.

WideStringBenchmarks

UTF-16 marshalling. .NET strings are already UTF-16 internally and NUL-terminated, so char* + fixed is genuinely zero-copy — the runtime just pins the string interior and passes its data pointer. Expect this to be the cheapest variant by a comfortable margin at small payloads.

LibraryImport_ROSpan uses ReadOnlySpan<ushort> because char isn't blittable without DisableRuntimeMarshalling; callers cast via MemoryMarshal.Cast<char, ushort>. StringBuilder is still around for legacy reasons but is the slowest path here.

StructBenchmarks

Two struct sizes (Point = 8 bytes / two int, Rect = 16 bytes / four int) crossed with by-value, in, ref, raw pointer, and a ReadOnlySpan<Point> array variant. Both structs are blittable so the marshaller hands them off without conversion.

The interesting axis is the size threshold: on Windows x64 anything larger than 8 bytes is passed by hidden pointer (caller copies onto stack, passes a pointer), while SysV (Linux/macOS x64) keeps using registers up to 16 bytes. Expect the ByVal_Large bar to be visibly worse than In_Large on Windows.

CallbackBenchmarks

Native-calls-managed — the marshaller has to produce a native-callable function pointer for the target. Four shapes, plus their variants with a void* userdata parameter:

  • DllImport_Delegate: pass a delegate parameter. The runtime synthesises (or caches) a reverse stub per call. Baseline.
  • DllImport_FunctionPointer_Cached: precompute the function pointer via Marshal.GetFunctionPointerForDelegate, pass as IntPtr. Skips the per-call stub work.
  • DllImport_FunctionPointer_PerCall: same but does the GetFunctionPointerForDelegate on every call. Shows the registration cost.
  • DllImport_UnmanagedCallersOnly: delegate* unmanaged<> pointing at a [UnmanagedCallersOnly] static method. No delegate object, no reverse stub, no GC handle. Should be the cheapest.

The userdata variants exercise the standard C callback shape cb(void* ctx, int arg). Cost should track the no-userdata variants closely — the extra argument is in a register.

PrimitiveBenchmarks

Two distinct concerns lumped together:

  • Bool widths. .NET's default bool marshals as 4-byte Win32 BOOL. [MarshalAs(U1)]/I1 gives the 1-byte C _Bool shape. VariantBool is the COM 2-byte convention. [MarshalAs(I4)] on bool is rejected at runtime — bool only pairs with I1/U1/Bool/VariantBool. Passing a raw byte instead of bool sidesteps the marshaller entirely.
  • Scalar pass-through. int, long, float, double through both DllImport and LibraryImport. All blittable, all in registers on x64. Tiny variation between them mostly reflects calling convention details (integer regs vs SSE regs) rather than marshalling cost.

ReturnStringBenchmarks

Library-owned static string returns. The direct return string shape from DllImport/LibraryImport is deliberately omitted: the runtime calls CoTaskMemFree on the returned pointer, which crashes when the library returns a static buffer. The correct shape is IntPtr + Marshal.PtrToString*, which gives the caller full control over decode and lifetime.

The cheapest variant (LibraryImport_IntPtr_SuppressGC + PtrToStringUTF8) skips both the GC handshake and the encode-time check — useful when you have a hot path that returns a known-safe pointer.

OutRefBenchmarks

Five spellings for "give the native side a pointer to write an int into": out int, ref int, raw int* with fixed, stackalloc Span<int>, and explicit IntPtr via Marshal.AllocHGlobal. Plus the inout variant where the native side reads and writes.

On modern runtimes out, ref, and int* collapse to the same generated call site. The IntPtr + AllocHGlobal variant is the slowest by a large margin — heap allocation + free per call.

HandleBenchmarks

Opaque handle round-trip — native receives a pointer and returns it unchanged. IntPtr is unmanaged: cheapest, but caller must guarantee the handle outlives every native call. SafeHandle is the right default for real OS handles: the runtime takes a ref-count on entry and releases on exit, guaranteeing validity for the duration.

The price of SafeHandle is roughly 3–4× IntPtr. SuppressGCTransition is incompatible with SafeHandle because the AddRef/Release dance needs a normal cooperative transition.

LastErrorBenchmarks

The cost of SetLastError = true — the marshaller captures GetLastError (Windows) or errno (POSIX) into a thread-local immediately after the native call so Marshal.GetLastWin32Error/GetLastPInvokeError can read it. One extra TLS write per call.

Worth comparing the "set but don't read" and "set and read" rows: most overhead is in the capture step, the read itself is cheap. Below the noise floor for most benchmarks, but real and measurable here against a noop baseline.

Cross-cutting findings

  • SuppressGCTransition is the single largest lever. At small payloads it drops the per-call cost from ~5 ns to ~1 ns. Only safe when the native side is short, non-blocking, and doesn't call back to managed.
  • Pre-encoded data beats runtime encoding by a large margin for strings. If you can hold a UTF-8 byte buffer alongside your .NET string, the cost is essentially a pin.
  • Function pointer + UnmanagedCallersOnly is the cheapest callback shape — no GC handle, no reverse stub, no delegate object. Use it for hot callback paths where the target is a static method.
  • Modern P/Invoke variants converge for blittable parameters. The choice between byte*, ref byte, Span<byte>, and byte[] rarely matters on net8+; readability wins.
  • Net48 keeps surprises — the legacy IL stubs took different paths for byte[] vs byte*/ref byte, and the array path is sometimes the faster one despite looking more "old-fashioned."
